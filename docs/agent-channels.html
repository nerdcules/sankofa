How sessions and agents talk to each other

Every agent runs in its own context window. The only thing that ever crosses the wall between two of them is plain text: a prompt going in, a report or message coming out. The figures below show each channel, what it carries, and where it stops.

Inside one session

Your main conversation can spawn four kinds of workers. In every case the worker's tool calls and intermediate results stay inside the worker. Only the arrow drawn in teal returns to you.

Between sessions

Separate Claude Code sessions can message each other too. The route depends on where the other session runs, and the route decides whether an answer can come back.

What never crosses a boundary

  • Plain text output. An agent's ordinary reply is seen by its user, not by other agents. Reaching another agent always means calling SendMessage.
  • Tool calls and intermediate results. They stay inside the context window that made them. You get the report, not the trail.
  • Permissions. Each session decides for itself. A message cannot approve a prompt, and asking a peer to do what your session was denied is permission laundering.
  • Attachments and commands. An @path in a message attaches nothing on the far side. A slash command arrives as words.
  • Configuration. No message changes settings, CLAUDE.md, or memory on the receiving side.

A conduit for many sessions

The channels above are ephemeral, text-only and blind to each other. A small daemon layer can be the team infrastructure a single technician lacks: the board, the lock, the reviewer and the build. It works only if it stays a substrate the agents write to, with hooks as the gates. It never decides anything itself.

The smallest set of parts

  • One binary. ledgerd owns a SQLite file under your state directory and listens on a Unix socket. Subcommands: claim, release, note, done, ask, events. The same binary runs in MCP stdio mode so any session can call it as a tool.
  • Four hook scripts. A lease check on PreToolUse for Edit and Write, a report check on SubagentStop, a handoff check on Stop, a test gate on TaskCompleted. Each is a few lines that call the CLI and exit 2 to deny.
  • One CLAUDE.md stanza. Claim before you edit, note before you stop, ask when you are unsure who owns a path. Hooks enforce it when the stanza is ignored.
  • Worktree by default. Spawn parallel work with worktree isolation so every workstream has its own checkout. The daemon watches them and flags two trees touching the same path.
  • Subscribers as you need them. A notifier is a loop over the event stream piped to the desktop. The dashboard and test runner come later and change nothing upstream.

Rules that keep it simple. Leases expire, so a dead agent cannot wedge the repo. The lease check is local and sub-millisecond, since it runs on every edit. The daemon records and answers and never coordinates, because a daemon that decides is one more context window you cannot see into.
